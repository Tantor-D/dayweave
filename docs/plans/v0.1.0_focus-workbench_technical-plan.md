# 个人专注工作台技术路线

## 文档的关键结论

本文确定 `v0.1.0 / focus-workbench` 的工程实现路线，与配套实施方案共同作为开发基线。用户已于 2026-11-03 授权全部 A—E 阶段，现已完成本地实现、模拟接口验证与浏览器验收；真实模型连接仍待配置后验证。

- 技术路线为 React + TypeScript + Vite 前端、Fastify 本地服务和共享的 Zod 数据定义；网页、AI 与命令行共用一套业务操作和文件保存逻辑。
- 原始 JSON、Markdown 文件是数据本体，不引入业务数据库；harness 是类似对象 setter 的规范操作工具层，不是对本地文件编辑能力的物理封锁。
- AI 修改由服务端执行可配置的确认策略，并经过格式、业务关系和版本校验；回溯以真实的修改前后内容为依据，恢复产生新记录。
- 首版完整交付本地工作台与通用 AI 工具入口；不引入云服务、自动同步或特定外部 AI 产品的运行框架。

## 2. 技术选择与运行方式

| 部分 | 选择 | 理由及限制 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite，普通 SPA | 适合状态丰富的桌面工作台；无 SSR、SEO 或云端框架需求 |
| 样式 | CSS variables、CSS Modules、主题注册表 | 玻璃材质与深浅色可独立调整，不把业务规则写进主题 |
| 时间看板 | 自有时间网格与 Pointer Events 交互 | 横纵方向、未定时区域和任意重叠共享同一模型，不依赖整套日历产品的布局约束 |
| 本地服务 | Node.js、Fastify 5 | 统一静态页面、HTTP 接口、模型请求、文件访问和事件通知 |
| 数据定义 | Zod 4，推导 TypeScript 类型并导出 JSON Schema | 同一份定义供前端、服务端及工具参数使用；关系和并发规则另外在业务模块校验 |
| 模型访问 | 服务端标准 HTTP 请求 | 首版只实现 Chat Completions 兼容协议，不引入代理运行框架 |
| 持久化 | UTF-8 JSON、Markdown、本地历史记录 | 文件可直接阅读和备份，无 SQL 或二进制业务数据源 |
| 自动测试 | Node.js 测试运行器，Fastify 请求注入 | 优先测试业务接口、持久化故障和协议行为；浏览器交互使用开发环境现有浏览器工具验收 |

依赖安装时采用满足上述主版本和本机 Node 要求的稳定版本，并提交锁文件；不把文档查询日的浮动 `latest` 当作可重复构建方案。

开发期前端由 Vite 提供热更新，`/api` 代理到本地服务；正式使用时构建前端，由本地服务同时提供静态页面与接口，浏览器访问一个地址。Vite 官方明确 `preview` 用于本地预览构建，不作为正式运行服务。[Vite 开发代理](https://github.com/vitejs/vite/blob/main/docs/config/server-options.md)、[静态构建说明](https://github.com/vitejs/vite/blob/main/docs/guide/static-deploy.md)

服务默认绑定 `127.0.0.1:4310`，端口可通过启动参数覆盖；端口占用时明确失败并提示调整，不悄悄连接未知服务。开发脚本负责一并启动前后端。正式路径为先构建，再通过一条启动命令运行服务，不需要用户维护两个终端。[Fastify 本机监听说明](https://github.com/fastify/fastify/blob/main/README.md)

## 3. 模块与文件组织

### 3.1 模块职责

```text
网页手工编辑 ────────────┐
网页 AI → 结构化提案 ────┼→ 本地 HTTP 接口 → 业务操作模块 → 文件保存模块 → 原始数据
外部 AI → harness CLI ───┘                       │               └→ 历史与恢复
外部 AI ───────────────────────────────直接读取原始数据
```

- **业务操作模块**：暴露小而明确的操作 Interface；负责状态转换、引用关系、版本约束、预览和审批决策，不依赖页面组件。
- **文件保存模块**：负责单写入队列、文件原子替换、历史记录、故障恢复和外部编辑检测。调用者不需要自己处理临时文件或锁。
- **AI 模块**：组装上下文、调用模型、解析提案；没有独立文件写入逻辑，也不能调整自己的审批设置。
- **harness Adapter**：把相同操作暴露给本地工具，通过 HTTP 连接正在运行的服务，不自行打开业务文件写入，不另起后台模型循环。
- **前端模块**：组织任务、时间看板、详情、设置和复盘；显示服务端返回的真实状态。暂时的拖拽预览不是已提交数据。

实现采用单个 npm 项目，不添加 monorepo 管理器或插件市场。核心目录如下；本机数据和运行目录在使用时生成。

```text
src/
  client/           页面、时间看板、主题、交互和客户端状态
  domain/           数据定义、业务操作、预览与差异计算
  server/           HTTP、持久化、审批、模型调用和事件通知
  harness/          本地命令入口
tests/              业务、持久化与协议测试，使用临时数据目录
docs/plans/         本次两份正式方案
data/               本机业务数据，支持启动时指定其他绝对目录
.local/             本机凭据、待确认提案和运行状态
dist/               构建产物
```

### 3.2 业务数据目录

```text
data/
  workspace.json                 项目、分类、任务和任务内的排期
  preferences.json               视图、主题、筛选、区域宽度
  ai/
    long-term.md                 长期背景
    short-term.md                短期安排
  reflections/
    daily/YYYY-MM-DD.md          每日反思
    notes/<id>.md                独立反思，标题在正文中
  .history/
    changes/<change-id>.json     提交前后内容、元数据及恢复状态
```

`workspace.json` 是任务业务数据的唯一真源；不同时维护另一份逐任务文件或浏览器数据库。把任务和排期收在一个文件中，是为了让一次跨任务改排可以整体校验、整体提交；个人工作台首版不预先承担多文件事务的复杂性。

JSON 使用两空格缩进、稳定字段顺序和末尾换行，ID 不随重命名变化。Markdown 保持普通文本，不为版本控制强塞 frontmatter；内容哈希和操作来源留在历史记录中。

数据、历史、本机设置及构建产物默认不纳入源代码 Git；实现时明确配置忽略项，不整体忽略所有 Markdown、测试或图片。未来可独立备份或同步数据目录，但首版不自动执行 Git 操作。API 密钥放在数据目录以外的 `.local/secrets.json`，仅当前用户可读，不在上下文、日志或导出中返回。

## 4. 核心数据契约

### 4.1 工作数据

| 类型 | 必要信息与约束 |
| --- | --- |
| Workspace | `schemaVersion`、递增 `revision`、工作区时区、分类集合、项目集合、任务集合 |
| Category | 稳定 ID、名称、排序；初始工作／个人，可新增和调整 |
| Project | 稳定 ID、标题、说明、分类 ID、排序及归档时间；不作为可排期任务 |
| Task | 稳定 ID、标题、说明、状态、优先级、项目或独立分类归属、排序、创建／更新时间、完成时间、归档时间、排期数组 |
| Placement | 稳定 ID，二选一的“仅日期”或“起止时刻”形式，归属于任务 |

状态为 `todo / in_progress / done`，优先级为 `P0 / P1 / P2 / P3`，默认 P2。独立任务保存分类 ID；项目任务保存项目 ID并从项目继承分类，不保存一份可能失配的冗余分类。分类归档前必须先迁移仍使用它的项目和独立任务；项目归档保留其任务和排期，通过归档筛选统一隐藏或查看，不删除历史。

排期采用判别联合：

```typescript
type Placement =
  | { id: string; kind: 'day'; date: string }
  | { id: string; kind: 'timed'; startAt: string; endAt: string };
```

日期采用 `YYYY-MM-DD`；起止时刻采用带时区信息的 ISO 8601 时间，保存时标准化为 UTC。显示按工作区时区转换，首版使用 `Asia/Shanghai`；不加入跨时区协作或自动时区迁移。

同一任务同一天最多一条未定时安排；重复添加时返回已有记录，不创建重复占位。同一任务允许多个定时安排，不禁止它们相互重叠。拖动既有安排时保留其 ID；日期与定时形式转换不是复制。拖回已有同任务未定时条目的日期时合并到该条目，并在同一次提交中移除原时间块。

完成任务写入完成时间，重新打开任务时清空当前完成时间；历史中保留真实的完成／重新打开事件，供“某天完成了什么”查询。恢复快照不伪造新的完成事件，撤销或更正可在关联历史中查看。复盘中的排期使用当前保存版本；旧排期通过历史版本查看，不实现每天自动冻结日报。拖拽／拉伸默认最短时长及吸附为 15 分钟；表单可输入分钟级时间，业务约束只要求结束晚于开始。

### 4.2 文本与设置

- 文档通过逻辑引用定位：长期背景、短期背景、某日反思或独立反思 ID。服务端负责映射文件，工具不能提交任意磁盘路径。
- Markdown 以原始 UTF-8 内容的 SHA-256 作为版本标识；创建新文档要求目标不存在，修改现有文档必须携带读取时的哈希。
- 视图偏好与业务任务分离。模型配置、审批策略和工具凭据属于本机用户设置，AI 操作列表不包含修改这些设置的能力。
- Zod 定义采用可直接表达为 JSON 的类型；日期保存为字符串，不把 `Date`、转换函数或自定义运行时对象作为公开格式。导出 Draft 7 JSON Schema 给 HTTP 与工具使用，跨记录引用等规则由业务模块继续校验。[Zod JSON Schema 导出及限制](https://github.com/colinhacks/zod/blob/main/packages/docs/content/json-schema.mdx)
- `schemaVersion` 与软件版本分开。首版只接受已知数据版本；不识别的新版本只读提示，不用空数据覆盖。未来迁移必须先备份并记录版本变化。

## 5. 规范操作与 harness 契约

### 5.1 操作层

提供语义明确的操作族，而非让 AI 生成文件路径、任意脚本或不受约束的全文替换：

| 操作族 | 能力 |
| --- | --- |
| 分类／项目 | 创建、编辑、调整分类与排序、归档及恢复 |
| 任务 | 创建、更新说明与归属、设置状态／优先级、调整排序、归档及恢复 |
| 排期 | 增加、调整起止或日期、转换形式、移除 |
| 文本 | 创建反思、更新指定背景或反思；修改携带内容哈希 |
| 历史 | 查询、预览恢复、提交恢复 |

一次工作数据提案可以包含多个任务操作，但必须全部作用于同一个工作数据快照。一份文本提案只操作一篇文档。跨文档请求拆成带依赖关系的多份提案，各自记录结果，不向用户承诺跨文件整体原子性。

预览由业务模块在当前快照副本上执行操作，产生实际 `before/after` 差异。模型自己的描述只能作为补充说明，不能替代差异。提案绑定目标、操作、基准版本、基准哈希及内容摘要，确认后不能悄悄换成另一套操作。

### 5.2 对外 Interface

| Interface | 主要输入／输出 |
| --- | --- |
| `read` | 目标与筛选 → 数据、版本、哈希 |
| `context` | 日期范围、显式任务范围、已选反思引用 → 两类背景、相关任务、版本与引用清单 |
| `preview` | 操作列表、目标、读取时版本／哈希 → 提案 ID、真实差异或错误 |
| `submit` | 提案 ID、请求 ID → `pending_confirmation / applied / conflict / rejected / failed` 及结果 |
| `confirm / reject` | 网页用户选择提案 → 按最新策略和版本重新验证后执行或拒绝 |
| `history` | 目标、分页 → 历史摘要及按需获取的差异 |
| `restore` | 目标历史版本、当前版本 → 恢复提案；仍通过同一提交规则 |

HTTP 路由集中在 `/api` 下，分为工作数据、文档、提案、历史、用户设置、AI 对话和事件通知。网页与 CLI 共享请求类型和错误码；错误至少区分校验失败、版本冲突、需确认、能力不支持和保存失败。外部 AI 不通过参数自称“用户手工编辑”来跳过确认。

第一版提供 `read / context / preview / submit / history / restore` 本地命令，默认输出 JSON；操作负载从 stdin 或明确指定的输入文件读取，不要求把大段 JSON 拼进命令行。CLI 仅连接运行中的本地服务，连接失败时返回可识别错误和启动提示；命令成功返回提案或修改编号，方便外部 AI 追踪结果。请求 ID 用于去重，超时重试不会重复创建任务或时间块。

正常 HTTP 写入采用本机来源检查与请求凭证；浏览器操作和 harness 采用不同来源标识，服务端决定审批规则。工具凭据不进入业务数据。该设计防止普通调用绕过流程，不把它宣传为能抵御拥有同一用户文件权限的本地程序。

### 5.3 直接编辑文件的边界

用户的 setter 类比是本方案的设计依据：原始文件可读且物理上可改，harness 提供推荐、可维护的正式修改路径；不锁死文件或通过隐藏格式阻止外部 AI。

应用维护最近一次有效内容，提交前比较实际文件哈希。目录变化检测触发重新检查，但不依赖文件监听事件保证一致性；读取和提交时仍核对磁盘内容。检测到入口之外的改动时暂停该目标的标准写入，展示差异并请求用户采纳或恢复；非法数据不替换有效状态。

采纳外部编辑先执行同样的校验，再记录为“外部导入”，不标记成已审批的 AI 操作。恢复或采纳前再次检查哈希，不能覆盖新出现的未知内容。外部直改之间的每一个中间版本无法保证被捕获，完整逐次回溯仅覆盖规范入口产生的修改及被显式采纳的最终外部版本。

外部 AI 直接读取文件后，需要重新读取才能获知新状态；本地服务不承诺能给任意外部模型自动刷新上下文。提供数据说明、格式 Schema 和使用约定，明确真源文件、背景读取顺序及写入方法；历史目录和反思正文不属于默认上下文。

## 6. 持久化、确认与恢复

### 6.1 保存事务

单个服务进程持有数据目录的写入锁，所有保存进入串行队列；第二个指向同一数据目录的服务实例拒绝写入。工作 JSON 使用版本加内容哈希，Markdown 使用内容哈希，不能只比较文件修改时间。

每次提交遵循以下顺序：

1. 在锁内重读目标，核验基准和当前审批策略，对完整结果执行格式与业务校验。
2. 生成包含前后内容、哈希、来源、时间和确认方式的 `prepared` 恢复记录；恢复记录保存失败则不修改目标。
3. 在目标同一文件系统写临时文件、完成必要同步，再原子替换目标；工作数据的 `revision` 递增。
4. 将恢复记录标记为 `committed`，再返回成功并通知网页刷新。提交结果不确定时返回可查询状态，不要求用户盲目重新创建操作。

普通重复提交通过请求 ID 返回原结果。准备记录是故障恢复依据，未确认提案不是已提交历史。对文件系统故障只报告实际完成的结果，不声称绝对防止硬件损坏导致的数据丢失。

### 6.2 启动恢复

启动时先检查未完成的恢复记录，再接受写入：目标哈希等于 `before` 时认定尚未应用，等于 `after` 时补齐提交状态；两者都不同则保留现场并要求显式处理，不自动覆盖。损坏文件不能触发“初始化为空数据”。首次空目录初始化与已有目录损坏分别处理。

撤销最近操作和恢复指定版本都走同一业务保存模块。工作 JSON 恢复内容时生成新的递增版本，不倒退 revision；Markdown 恢复保存为新的修改。历史记录首版不自动清理，界面可提示历史空间占用，清理和备份策略后续单独确定。

### 6.3 审批与状态通知

AI 审批模式为 `require_confirmation` 或 `auto_accept`，默认前者。无论网页 AI 还是外部 harness，服务端提交时读取最新模式；手工 UI 编辑无需再次确认。

待确认提案持久化在本机运行目录中，刷新或重启不丢失。生成提案后若目标变化，原提案转为冲突，必须重新读取并生成差异。策略改为自动接受不会批量静默执行此前积压的提案；用户可显式重新提交。

通过服务端事件通知网页提案、数据版本和历史发生变化；连接重建后重新读取快照，事件本身不是唯一数据源。通知不包含密钥或不相关的反思正文。

## 7. 前端实现要点

### 7.1 时间坐标与交互

将数据到坐标的换算抽成纯函数：输入日期范围、时间刻度、方向及网格尺寸，输出时间块矩形和命中结果。横向、纵向视图复用同一换算和操作命令；跨日块先切成展示片段，再映射回原 Placement ID。

使用区间重叠分组分配并排通道，不把重叠数作为有效性约束；空间不足时允许区域滚动和打开详情，不截断数据。未定时区域单独布局，不进入重叠计算。

拖拽和拉伸期间只修改本地预览，指针释放时提交一次操作；取消时恢复。服务端成功后接纳新快照，冲突或失败时回退并说明原因。表单提供相同能力，键盘可操作主要按钮，不要求所有修改必须用鼠标拖拽。

### 7.2 状态、主题与布局

首版不引入全局状态框架：用 React 状态与 reducer 维护已确认快照、临时交互和视图偏好，服务端是业务状态权威。三个层次不混存，避免筛选和拖动产生隐式业务写入。

`ThemeDefinition` 定义主题 ID、深浅模式、颜色、字体、间距、圆角、阴影和材质，并允许替换有稳定输入输出的卡片外观；不得访问保存模块。`ViewLayout` 组合任务面板、看板和详情区域，接收统一视图模型与操作函数，不重复实现任务规则。

首版只注册玻璃拟态浅色、深色和一个工作台布局；扩展点服务于用户已明确的后续多风格需求，不同时开发多套布局或主题插件系统。优先级颜色使用语义变量，任何主题都保留文字标签和完成状态。背景模糊不可用或用户减少动态效果时采用不透明表面及简化动画。

## 8. AI 调用、上下文与隐私边界

### 8.1 兼容协议

配置 API 基础地址、模型名和密钥，服务端调用 Chat Completions。基础能力为普通消息请求与文本响应；工具调用作为可探测的增强能力，不假设所有标称兼容的供应商都完整支持。首版不依赖流式传输，提供请求中状态、取消和超时处理。

具备工具调用能力时只提供结构化 `propose_changes` 工具，将语义操作转为提案；工具调用不等于已经执行。服务端解析和校验参数，禁止把任意脚本、模型生成路径或自然语言当作写入指令。无工具能力时回退为纯聊天，明确禁用“应用变更”。不依赖 `strict` 参数代替本地业务校验。[Chat Completions 工具协议](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)

### 8.2 上下文构造

每次模型请求按以下顺序组装：当前两类背景、用户明确的任务范围和版本、当次选择的反思正文、当前对话及操作要求。范围默认从当前视图关联任务开始，在聊天面板明确列出并允许调整；看板筛选不构成模型的隐式权限系统。

历史对话中旧的任务快照不当作最新状态；确认提案前重新校验版本。两类必读背景超出上下文预算时提示缩短或调整模型，不静默丢弃其中一类。反思仅使用当次显式选择项；新一轮普通对话不自动沿用已取消选择的正文。

为避免旧反思正文通过聊天历史继续泄露，服务端保存对话消息与来源标记，发送历史时剔除已取消选择的原始附件内容；如果先前模型回复已包含该文档内容，则提示继续使用当前会话会携带已有讨论，允许新建不含该内容的会话。取消选择不能撤回此前已发给供应商的内容。

外部 harness 的 `context` 返回两类背景和显式范围；使用说明要求执行改排前获取最新上下文。应用能保证其提供的上下文内容，不能保证任意直接读文件的外部模型真的阅读或理解每个文件。

### 8.3 本机与外部服务

本地保存不等于模型推理也在本地：调用用户配置的远程接口时，会发送本次上下文。聊天面板展示接口地址和上下文范围；密钥保存后只返回“已配置”状态，应用日志不记录密钥、授权头或完整正文。密钥由服务端使用，不置于前端构建和浏览器持久化中。[OpenAI 认证说明](https://developers.openai.com/api/reference/overview)

确认策略、供应商设置和凭据只能由用户设置入口修改；修改业务数据的工具不暴露这些操作。反思内容作为数据交给模型，不具有更改工具权限或审批模式的效力。

### 9.1 自动测试

- 数据规则：独立／项目任务归属、优先级、状态转换、引用缺失、归档恢复、未定时去重、合法重叠、跨午夜、UTC 与工作区日期换算。
- 保存与并发：多个过期版本、文件哈希不匹配、请求去重、恢复记录失败、目标写入失败、替换后异常、启动时 before／after／未知内容三种恢复状态。
- 审批：默认需确认、自动接受、策略在提案期间变化、旧待确认提案不自动批量执行、确认时冲突、AI 设置修改被拒绝。
- 回溯：完整差异、恢复整个工作快照的范围、Markdown 单文档恢复、恢复增加版本和历史、外部编辑采纳与非法文件保留。
- AI：使用模拟 HTTP 端点验证两类背景始终在请求内、反思未选不发送、旧附件范围处理、工具能力降级、非法参数、超时取消和模型失败不写业务文件。
- harness：与网页使用同一业务模块，服务未运行有明确错误，stdout 可解析，重试不重复创建操作。

测试只使用临时目录和模拟密钥，不读取用户真实反思，也不为验证而调用付费模型。真实兼容接口连接测试在用户配置后进行；没有凭据时报告该项未验证，不影响其他已验证结果的报告。

## 10. 当前交付与后续边界

本次已获业务代码、安装依赖、本地 Git、运行和验收授权。沿用同一个版本完成 A—E 阶段，不创建远程、不推送、不部署。文档查询、验收截图、日志及测试数据只留在忽略目录或系统临时目录。

第一版之外的云同步、循环任务、计时、完整额外主题以及特定 harness／MCP 对接继续单独讨论；本方案不为这些可能性预先搭建额外平台。

### 10.1 实施细化

- 启动与测试使用 `node --import tsx`，避免依赖 tsx CLI 的额外 IPC 服务；正式使用仍由 Fastify 统一提供构建后的前端和 API。
- 依赖精确版本记录于 package.json 和 package-lock.json；`@fastify/static` 的间接 `glob` 固定到 `14.0.3`，避开其旧依赖的已知漏洞，并验证静态资源服务。
- 浏览器会话使用来源检查、短期请求凭证与仅用于事件流的 HttpOnly Cookie；harness 使用 `.local/harness-token`，服务端根据凭证确定来源，忽略客户端自称的用户身份。
- `.local/known.json` 保存最近有效内容用于识别重启前后的外部编辑；它是可验证的保护快照，业务真源仍为 data 下的 JSON 与 Markdown。
- 提案绑定操作、ID 和业务字段；创建、更新及完成时间是服务端元数据，以实际提交时刻为准，预览界面明确提示，历史记录最终真实内容。恢复快照保留原有时间，不伪造新的完成事件。
- 开发命令同时启动 Vite 和 API；前端热更新，后端改动后重启命令。后端启动失败时同时结束前端，避免代理到被占用端口的未知服务；`PORT` 同时配置后端与开发代理。
- `.local` 必须位于数据目录之外。会话消息只保存在服务内存，重启后新建对话；业务内容、提案和历史持久化。新建 Markdown 的修改前版本恢复为空文档，旧内容仍在历史中。
